# Agent-dispatch task queue: who owns what

The dsh sidebar's task chip shows the agent-dispatch queue of this host and lets kcn
steer it. Three parties touch that queue; this page is the contract between them.

| Layer | Where | Owned by | Why there |
|---|---|---|---|
| Plugin source | `examples/dsh/packages/clawock-dsh/src/` | git (this repo) | reviewed code, CI |
| Chat rendering | `examples/dsh/packages/clawock-dsh/src/{desk,panel,text,openclaw}.ts` | git (this repo) | the same package is an OpenClaw plugin: `/dispatch-list` prints the chip's panel as text — the dsh gateway's services (`desk.ts`), the sidebar's view model (`panel.ts`), a text renderer (`text.ts`). OpenClaw loads the installed package through `plugins.load.paths`; read-only |
| Plugin build artifacts | `examples/dsh/packages/clawock-dsh/lib/` | git, regenerated by `npm run build` | dsh loads them without a build step; CI fails on any drift |
| Queue ops entry | `ops/host/task_queue_ops.py` (+ `model_prices.json`) → installed under `/root/tools/agent-dispatch/` | git; installed by `ops/host/install_task_queue_ops.sh` | the only code that writes to a task on behalf of the UI, and the only place the queue order is decided — so it is versioned and tested |
| Installed plugin | `~/.dsh/profiles/<profile>/node_modules/clawock-dsh` | `ops/host/install_dsh_plugin.sh` | generated from a packed tarball; never edited by hand |
| Runner | `ops/host/agent-dispatch/` (`run-agent.sh`, `dispatch.sh`, helpers, `templates/`, its own `tests/`) → installed as `/root/tools/agent-dispatch/`, path for path | git; installed by `ops/host/install_agent_dispatch.sh`, which `refresh_live.sh` runs whenever the installed copy fails its `--check` | tasks execute these files while they are replaced, so every file is installed by rename with a `.before-update` copy; see [The runner](#the-runner) |
| Host policy | `/root/tools/agent-dispatch/limits.env` | host-local, not in git | live admission policy read by the runner, the ops entry and clawock-patrol; see [What stays on the host](#what-stays-on-the-host) |
| Runtime state | `/root/logs/agent-dispatch/<id>/{meta,result,override}.env`, `run.log`, `audit.log`, `.queue/` | the runner and the ops entry | changes every few seconds; never committed |
| Secrets | `/root/tools/agent-dispatch/notify.env` (targets), provider keys | host-local | never in git, reports or memory |

The live checkout (`/root/.openclaw/workspace`) is fast-forwarded by cron all day, so it
is the *repository's* copy of the ops entry and the runner, not the running one. Merging
installs nothing under `/root/tools/`. `refresh_live.sh` (the step that applies a merge to
this host) installs the runner whenever the installed copy differs from the checkout, compared
by content, because cron's pushes fast-forward the checkout too; the ops entry is still
installed by hand, and the chip shows when it lags (see *Version skew*).

## The ops entry

```
task_queue_ops.py [--json] [--source ui|cli|runner] <action> ...
  version            {"ops_version": <sha256 of the file, 12 hex>, "api": N}
  list               per agent: lock holder, queue in order, quota hint, tasks it cannot order
                     (`unqueued`); host file hashes
  head <agent>       the task id that takes <agent>'s lock next ("" when nobody waits)
  cancel <id>        stop a task
  priority <id> <n|top|up|down|reset>
                     reorder a waiting task within its agent's queue
  model <id> <model|keep|default> [<effort|keep|default>]
                     the model/effort of the task's next attempt
  choices <id>       what `model` accepts for this task, and whether it may change now
  retry <id>         continue an ended (failed/cancelled/timed-out) task's session as a new task
  append <id> [--queue] [--text T]
                     add an instruction (stdin) to a live task, same session (dispatch.sh append)
  log <id> [--lines N]   the end of run.log, redacted
  result <id>        the latest final report (read-result.py)
  usage <id>         tokens used and their API-price estimate (text: the result.env lines)
  brief <id>         prompt.md and the appends (inbox/, inbox/delivered/), capped at 64 KB
  deadline <id> <+Nh|+Nm|YYYY-MM-DD HH:MM|reset>
  attempts <id> <n|reset>
  resumes <id> <n|reset>
                     the task's deadline / retry budget / quota-resume budget (runner api 3)
```

Exit codes: `0` ok · `2` usage (bad id, bad value) · `3` refused (task ended, action not
allowed for this task) · `4` unknown or pruned task · `5` host failure (systemctl, a write)
· `6` busy (another write to the same task is in flight). With `--json` every action,
failures included, prints one object; failures are `{"ok": false, "code": N, "error": "…"}`.

Every write appends one line to the task's `audit.log`: time, `source=ui|cli`, action,
what changed, and the `ops_version` that did it. Writes to one task are serialised by a
non-blocking lock on `<task>/.ops.lock`; a second write while one is in flight answers `6`.

### cancel

- Only a known task id (`^[a-z0-9][a-z0-9-]*$` with a `meta.env`); anything else is `2`/`4`.
- Unit not active: `ok` if the task already says `cancelled` (idempotent), else `3` with
  its terminal state.
- Unit active: `systemctl stop --no-block`, then up to 4 s for the runner's `on_signal` to
  write its terminal state (`pending: true` if it has not yet). A `cancel-requested`
  marker younger than 30 s makes a repeat a no-op instead of a second stop.
- `was` says what was lost: `queued` (nothing ran — free), `sleeping` (a quota or retry
  wait; the session is kept), `running` (the current step's unsaved progress is lost).
  `session` and `resume` give the command that continues the session.

### priority

Only a live task of the current runner (`RUNNER_API=2` in its `result.env`) that is
waiting for its agent lock, or asleep on a quota/retry wait (the value then applies when
it re-queues). Refused (`3`): ended tasks, tasks without `RUNNER_API=2` (their runner would
ignore the value), patrol rounds, and a task already running. `top` sets one above every other
reorderable waiter; `up`/`down` swap with the neighbour and renumber the reorderable
waiters so exactly that swap happens (every task whose value changed gets its own
`audit.log` line naming the move); `reset` removes it; an integer sets it (−99..99). A
protected task (below) is not reordered, and nothing can be moved in front of it: that
answers `ok` with `changed: false` and says why. The answer carries the new order.

### model / effort

Written to the task's `override.env` (`MODEL=`, `EFFORT=`) and read by the runner before
**every** attempt, so it applies to the next attempt — the attempt running now keeps its
model. Precedence: an explicit override > the fallback pool > the dispatched default (an
override model becomes the pool's head; failures after it rotate through the rest of the
pool like the ordinary fallback switch). `default` clears a value; `keep` leaves it.
Legal values come from each agent's own source, never a list kept here:

| Agent | Models | Effort flag and values |
|---|---|---|
| claude | the task's own, dispatch.sh's default, those this host has dispatched, the aliases in `claude --help` | `--effort`, the list printed by `claude --help` |
| codex | the task's own, dispatch.sh's default, the visible models in `~/.codex/models_cache.json` | `model_reasoning_effort`, that model's `supported_reasoning_levels` |
| opencode | the task's own, the pool file `opencode-fallback-models` | `--variant`: none (the free pool has no variants) |

Changing the model of a session on resume was checked for claude (`--resume` with another
`--model` continues the same conversation, 2026-09-26) and is what opencode's fallback
does every patrol round (`-s` on the next pool model). It is **not** verified for codex
(its weekly quota was out), so a codex task can change model/effort only before it has a
session.

### retry, append, log, result

`retry` runs `dispatch.sh append <id>` with a fixed "continue from the real state" text on
an ended task that recorded a session and did not finish `ok/DONE`; without a session it
answers `3` (dispatch it again). `append` delivers to a live task only (the chip's
"wrap up" button sends a fixed wrap-up instruction with `--queue`); ended tasks go through
`retry`. `log` and `result` are read-only and redact tokens the way the runner does.

### usage — tokens and an estimate, not a bill

`usage` reads the agent's own session record and never guesses:

| Agent | Record | What is counted |
|---|---|---|
| claude | `~/.claude/projects/*/<session>.jsonl`, each assistant line's `message.usage` | deduplicated by message id (claude repeats one API message's usage on every content-block line); cache writes split into 5-minute / 1-hour by `usage.cache_creation` |
| codex | `$CODEX_HOME/sessions/**/rollout-*-<session>.jsonl`, `token_count` events | `total_token_usage` is cumulative per process: repeats add nothing, a resumed process restarts from zero; `cached_input_tokens` is part of `input_tokens` |
| opencode | `~/.local/share/opencode/opencode.db`, table `message` | `tokens.input/output/reasoning/cache.read/cache.write` and opencode's own `cost` |

The session is `SESSION` in `result.env` (older tasks: `session_id` in `attempt*.json`). Only
messages from the task's dispatch time (`meta.env CREATED`) on count, because a retried task
resumes an older session. The price per model is `ops/host/model_prices.json` (source and date in
the file, installed next to the entry): the amount is **what the tokens would cost at API list
prices**, an estimate — claude and codex run on subscriptions here, and no subscription price is
in the table. claude rows come from Anthropic's API price table; codex's `gpt-*` rows (2026-09-28)
from OpenAI's API pricing page (`sources.openai` in the file: URL, date, standard short-context
tier; its cached-input rate is `cache_read`). A model without a row keeps its tokens and has no
amount (`—` on the chip), never a guessed one; an
opencode task is `free` when opencode reports cost 0 and every model is in the free pool file or
ends in `-free`. Checked on a real task: the estimate for `add-side-aggression-20260926-151620`
($14.02) equals the `total_cost_usd` claude itself reported for that session.

The runner (api 3) runs `usage` after every attempt and at the end, and keeps the answer in
`result.env` (`TOKENS_IN`, `TOKENS_CACHE_W`, `TOKENS_CACHE_R`, `TOKENS_OUT`, `TOKENS_TOTAL`,
`COST_USD`; empty when nothing was found). A live task's figures are therefore as of its last
finished attempt.

### brief — the task's instructions, read-only

`brief` answers `prompt.md` (the brief as dispatched, with its dispatch contract) and every append:
`inbox/*.md` not delivered yet, `inbox/delivered/*.md` delivered, in file-name (time) order. The
answer is capped — the brief at 48 KB, the appends at 16 KB together — and says so, with each
file's path so a reader can open the whole file. In JSON: `truncated` (prompt.md was cut; its real
size is `brief_bytes`), each append's own `truncated` and `bytes`, and `appends_truncated` /
`dropped_bytes` for the whole answer. In the default text answer, each cut file's header carries
`[truncated: <real> -> <shown> bytes; full text: <path>]`, and a last line gives the bytes not
shown. Before #1988 the text answer dropped them without a word, exit 0. Nothing edits a brief: change a queued task's `prompt.md` before it starts, or
`dispatch.sh append` (`--queue` while it runs).

### deadline, attempts, resumes — the task's budgets

| Budget | Owner of the dispatched value | Changed by | Bounds |
|---|---|---|---|
| deadline (`DEADLINE_EPOCH`) | `meta.env` (dispatch.sh, at most 72 h after dispatch) | `deadline <id> …` | ≥ now + `MIN_RUN_SEC` + `KILL_MARGIN` (600 + 70 s); ≤ dispatch + 72 h (the dispatch ceiling kept); an expired deadline is never moved earlier |
| retries (`MAX_ATTEMPTS`) — failed or stalled attempts | runner default 3 (`meta.env` may carry one) | `attempts <id> n` | 1..10, not below the attempts already made |
| quota resumes (`QUOTA_RESUMES`) — each one replays the session's context | `meta.env` | `resumes <id> n` | 0..6, not below the resumes already used |

The two retry budgets are different money: a retry re-runs a failed attempt; a quota resume
continues the session after a quota wait and pays to replay its context (cache reads).

The entry writes the new value to `override.env` (`reset` removes it; a value equal to the dispatch
record is not stored) and audits it. A runner of **api 3** rereads these keys at every poll of its
lock wait and before every attempt, and publishes what it uses in `result.env`
(`DEADLINE_EPOCH`, `MAX_ATTEMPTS`, `QUOTA_RESUMES`) — the chip shows those, not the dispatch record.
When it applies:

- **waiting** (queued for the lock, asleep on quota/retry): at the next poll, seconds;
- **running**: the attempt in flight keeps the time cap it started with; the change applies to
  the next attempt and to every wait after it;
- **runner api 2** (started before api 3 was installed): refused (`3`). It read `meta.env` once at
  start and armed its outer `timeout` from the deadline, so the change could not apply.

A write to an ended task is `3`; a value out of bounds is `2`. Nothing restarts the task's unit.

What made this necessary (a real attempt, 2026-09-27, to carry three queued tasks past a weekly
quota reset):

- `meta.env` is sourced **once**, when the runner starts; editing it changes nothing for a live
  task. `prompt.md` is read at the start of **every attempt**; do not confuse the two.
- The unit is a transient `systemd-run` unit: `systemctl restart` answers `Unit … not found`. It
  can only be recreated as dispatch.sh does (`systemd-run --unit agent-dispatch-<id> --collect
  --quiet --description "agent-dispatch <agent>: <name>" -p TimeoutStartSec=infinity
  -p TimeoutStopSec=90s -p KillMode=control-group /root/tools/agent-dispatch/run-agent.sh <dir>`).
- A restart loses `QUEUED_AT` (kept in memory and `result.env`; a new runner does not read it
  back), so the task loses its place in the queue.
- A runner before api 3 wraps itself in `timeout -k 80 $((deadline - now - 10))` at start: a
  later deadline in any file does not stop that timer. Api 3 arms the outer timer at the
  dispatch + 72 h ceiling instead and enforces the deadline itself (attempt caps, lock and slot
  budgets, quota and retry sleeps all read the current value).
- Stopping a runner with TERM runs `on_signal` → `finish()`, which sends a "cancelled"
  notification that is not true for a restart; SIGKILL sends none but writes no terminal state
  either. Neither is a way to change a budget — that is why the change goes through
  `override.env` and never through a restart.

### Queue order

Each agent has its own lock, so each agent has its own queue; orders never mix across
agents. Among the tasks waiting for one agent's lock:

1. `patrol-*` rounds always go last — their priority is ignored.
2. A manual task that has waited `QUEUE_FAIR_WAIT_SEC` (limits.env, default 14400 s) is
   *protected*: it goes before every unprotected task, and nothing can be placed ahead of
   it any more. A task can only be overtaken during its first hours, so priority cannot
   starve anyone.
3. Protected tasks in `QUEUED_AT` order; the others by `PRIORITY` (higher first), then
   `QUEUED_AT`, then id.

`QUEUED_AT` is when the runner first started waiting (epoch seconds, `result.env`). The
runner registers a waiting task as `.queue/<agent>/<id>` (`PID=`, `QUEUED_AT=`) in its lock
directory and removes the entry when it takes the lock or ends; an entry whose PID is gone
does not count. The lock holder writes `.queue/<agent>.holder` (`ID=`, `PID=`, `SINCE=`).
The runner looks one poll after it (re-)enters the queue, so tasks that enter together
(at a quota reset) are all registered before one is picked; if the entry is missing or
fails, a manual task takes the lock when it is free (the old behaviour) and a patrol round
still never takes it while a manual task of its agent is registered.

### Tasks without RUNNER_API 2

Only a task whose `result.env` says `RUNNER_API=2` registers in `.queue/`, writes
`QUEUED_AT` and honours `override.env`. A live task without it (a runner from before
2026-09-26, or one started by hand) is never shown as an empty queue (kcn 2026-09-26):
`list` names it under its agent's `unqueued` with the reason, `head --json` adds it to its
`note` (the bare-id text answer the runner reads is unchanged), and `priority`/`model`
refuse it (`3`). A held lock without a live holder file is reported as
`held: true, id: null` with a note, never as free.

Until 2026-09-27 the entry also parsed such tasks' `run.log` (`waiting for <agent> lock`,
`lock held`) to place them first in their queue, flagged `legacy`. That branch was removed
once no older runner was left (`list` showed no legacy row and every live `result.env`
had `QUEUED_AT` and `RUNNER_API`); the `legacy`/`holderLegacy` fields are gone from the
chip's wire too.

### Quota waits release the lock

A task that hits a quota limit sleeps until the reset **without** its agent lock (before
2026-09-26 it kept it: a claude task asleep on its 5-hour reset held `claude.lock` for four
hours while three tasks queued). It keeps its session lock (`session-<id>.lock`, taken as
soon as the session is known), so no second task can resume the same session meanwhile,
and it writes `.queue/<agent>.quota` (`UNTIL=`, `BY=`). A task that takes the lock while
that hint is in the future releases it again and waits for the same reset (plus two polls)
without spending an attempt, a quota resume or a notification — the limits are per
account. At the reset the sleeper re-queues with its original `QUEUED_AT`; the first
attempt that gets through deletes the hint.

## Runner fields the chip reads

`result.env`, besides `STATE/RC/OUTCOME/SESSION/ATTEMPTS/WAITING/SLOT/MODEL_USED/…`:

| Field | Meaning |
|---|---|
| `QUEUED_AT` | epoch the task first waited for its agent lock (queue order; kept across quota waits) |
| `WAKE_AT` | epoch a quota/retry wait ends (empty otherwise) |
| `EFFORT_USED` | the effort of the latest attempt (`MODEL_USED` is its model) |
| `NOTIFIED` / `NOTIFY_FAILED` / `NOTIFY_AT` | the legs (`weixin`, `telegram`, or an unknown name) of the latest notification that were delivered / failed, and when |
| `RUNNER_API` | `2` for a runner that honours the queue and `override.env`; `3` also rereads the budgets; absent before |
| `DEADLINE_EPOCH` / `MAX_ATTEMPTS` / `QUOTA_RESUMES` | the budgets the runner is using now (api 3; see *deadline, attempts, resumes*) |
| `TOKENS_IN` / `TOKENS_CACHE_W` / `TOKENS_CACHE_R` / `TOKENS_OUT` / `TOKENS_TOTAL` / `COST_USD` | the `usage` answer as of the last finished attempt (api 3); `COST_USD` is an API-price estimate, `free`, or empty |

`override.env` holds `PRIORITY`, `MODEL`, `EFFORT`, `DEADLINE_EPOCH`, `MAX_ATTEMPTS`, `QUOTA_RESUMES`
(written only by the ops entry);
`audit.log` one line per write.

## The runner

`run-agent.sh` runs one task inside a transient systemd unit that `dispatch.sh` starts
(`systemd-run --unit agent-dispatch-<id> … run-agent.sh <task dir>`): it waits for its agent's
lock in queue order, takes a run slot, runs the CLI attempt by attempt, handles quota waits,
retries, stalls and appends, writes `result.env`, and sends the notification. Its source is
`ops/host/agent-dispatch/`, laid out exactly like the installed directory:

```
ops/host/agent-dispatch/
  run-agent.sh  dispatch.sh            the runner and the host CLI (RUNNER_API=3)
  read-result.py quota.mjs             `dispatch.sh result`, the quota line in notices
  resource-pressure.sh                 memory-pressure reading shared with clawock-patrol
  probe-free-models.sh                 finds dead models in the opencode free pool
  opencode-fallback-models             that pool, in order (read at dispatch time)
  templates/review.md                  `dispatch.sh --template review`
  tests/run-tests.sh tests/bin/        fault-injection suite with fake claude/codex/opencode/openclaw
  tests/test_limits.py tests/test_read_result.py
```

It sits next to `task_queue_ops.py` but is a different install target: the ops entry keeps its
own installer and its own place in `ops/host/`.

```bash
ops/host/install_agent_dispatch.sh            # parse-check, then per file: .before-update, install by rename, cmp
ops/host/install_agent_dispatch.sh --check    # exit 1 when an installed file differs, or limits.env lacks a key
ops/host/install_agent_dispatch.sh --rollback # undo the last install that changed something (and only that)
```

The installer refuses to run when the host's `limits.env` is missing or lacks a key the runner
needs. It records what it replaced in `.install-agent-dispatch.last`, so a rollback does not
restore an older `.before-update` left by a hand edit. A running task keeps executing the
file it opened (a rename leaves that inode alone; an in-place copy would corrupt a bash script
mid-read); the next task starts on the new one.

Tests. `.github/workflows/dispatch-runner.yml` runs the suite on every PR that touches the
runner, the ops entry, either installer or `patrol.sh`. It stages the files at their host path
through the two installers and runs them as root, as on the host, one matrix leg per group.
It is not a required check, and its trigger is path-filtered so other PRs start nothing. By
default it runs `unit, names, notify, core, queue, slots, deadline, budget`: the longest,
`budget`, took 158 s on the first run, less than `validate`. `stall` (198 s) and `quota` (256 s)
are almost entirely real waiting: stall timers running out, a quota reset minutes away. They
run on demand (`workflow_dispatch` with `slow`), or on the host:

```bash
AGENT_DISPATCH_RUNNER=<staged run-agent.sh> DISPATCH_TEST_CASES=stall,quota \
  bash <staged>/tests/run-tests.sh
```

`tests/test_install_agent_dispatch.py` (in `validate`) holds the installer's file list equal to
the tracked files and checks install, `--check` and `--rollback` in a temp directory.

### What stays on the host

| Path under `/root/tools/agent-dispatch/` | Why it is not in git |
|---|---|
| `notify.env` | delivery targets (WeChat and Telegram recipients). Private to kcn, and the repository is public |
| `limits.env` | live policy with three readers: the runner (`MAX_RUNNING_<AGENT>`), the ops entry (`QUEUE_FAIR_WAIT_SEC`) and clawock-patrol (`MAX_RUNNING_OPENCODE`, `PATROL_MIN_AVAILABLE_KB`, `PATROL_MAX_MEMORY_FULL_AVG60`). Its values are this host's decisions, sized for its 2 GB, and are changed in place. A versioned copy would either overwrite a live change on the next install, or sit in the repository as a second, stale truth. The installer checks that the keys exist and never writes the file. The CI job writes its own fixture with the values the suite asserts |
| `task_queue_ops.py`, `model_prices.json` | versioned, but under `ops/host/` with their own installer (`install_task_queue_ops.sh`) |
| `*.before-update`, `.install-agent-dispatch.last` | rollback state of the last install on this host |
| `__pycache__/` | bytecode Python writes next to the helpers |

And everything under `/root/logs/agent-dispatch/` (task dirs, `run.log`, `result.env`,
`override.env`, `audit.log`, locks and `.queue/`): runtime state that changes every few seconds.

### Notifications

At the end of a task, and when it starts a quota wait, the runner sends one message per leg of
the task's `NOTIFY` list (`weixin`, `telegram`, both by default, `none` for patrol rounds).
Each leg is `openclaw message send --channel … --target …` with the targets from `notify.env`.
The legs run in parallel, each once, with a time limit: 60 s for the end-of-task and the
quota-wait notice, 30 s on the cancel path (bounded by the unit's stop budget).
Delivery is **best-effort**. A failed leg never changes the task's state, is not retried,
and raises no alarm. It is one `notify: send failed (<leg>)` line in `run.log`, and
`NOTIFIED` / `NOTIFY_FAILED` / `NOTIFY_AT` in `result.env`, which the chip shows as the
receipt icons. A failed leg means nobody was told. The task itself may be fine: read
`result.env`.

What the legs did from 2026-09-26 to 2026-09-28 (every `notify:` line in `run.log`):

- **WeChat** failed on every send from at least 09-26 03:25 to 09-27 20:52, and has
  delivered every send since 09-27 22:23. This is the known WeChat token problem: the
  per-conversation token behind the `openclaw-weixin` channel lapses, and every send fails
  until it is renewed. It is not fixed here and can come back.
- **Telegram** delivered every end-of-task notice. It failed four times, all on 30-second
  notices (three quota-wait notices, one cancel), each after exactly the 30 s limit. The CLI
  is slow to start on this host: a `--dry-run` of the same command, which sends nothing, took
  13 s alone and 25 s with both legs starting together. So a real send can take longer than
  30 s. Neither the configuration nor the network was the cause. The quota-wait notice has
  had 60 s since #2057; a cancel notice keeps 30 s, the most the unit's stop budget
  (`on_signal`) leaves, so on a busy host a cancel can still go unannounced on Telegram.

## Version skew

The chip shows the installed entry's `ops_version` next to the hash of the repository's
copy in the live checkout. If they differ, the entry was merged but not installed (or
edited on the host): run `ops/host/install_task_queue_ops.sh` (it saves the previous copy
and verifies with `cmp`), or `--rollback` to go back. `list` also reports the hashes of the
installed `run-agent.sh`, `dispatch.sh` and `limits.env`. The first two are versioned now:
`ops/host/install_agent_dispatch.sh --check` says whether they, and every other runner file,
match the checkout.
