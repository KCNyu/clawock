# Agent-dispatch task queue: who owns what

The dsh sidebar's task chip shows the agent-dispatch queue of this host and lets kcn
steer it. Three parties touch that queue; this page is the contract between them.

| Layer | Where | Owned by | Why there |
|---|---|---|---|
| Plugin source | `examples/dsh/packages/clawock-dsh/src/` | git (this repo) | reviewed code, CI |
| Plugin build artifacts | `examples/dsh/packages/clawock-dsh/lib/` | git, regenerated by `npm run build` | dsh loads them without a build step; CI fails on any drift |
| Queue ops entry | `ops/host/task_queue_ops.py` → installed as `/root/tools/agent-dispatch/task_queue_ops.py` | git; installed by `ops/host/install_task_queue_ops.sh` | the only code that writes to a task on behalf of the UI, and the only place the queue order is decided — so it is versioned and tested |
| Installed plugin | `~/.dsh/profiles/<profile>/node_modules/clawock-dsh` | `ops/host/install_dsh_plugin.sh` | generated from a packed tarball; never edited by hand |
| Runner and policy | `/root/tools/agent-dispatch/{run-agent.sh,dispatch.sh,limits.env,…}` | host-local, not in git | tasks execute this file while it is replaced; installs are atomic with a `.before-update` copy (see its own tests in `tests/run-tests.sh` there) |
| Runtime state | `/root/logs/agent-dispatch/<id>/{meta,result,override}.env`, `run.log`, `audit.log`, `.queue/` | the runner and the ops entry | changes every few seconds; never committed |
| Secrets | `/root/tools/agent-dispatch/notify.env` (targets), provider keys | host-local | never in git, reports or memory |

The live checkout (`/root/.openclaw/workspace`) is fast-forwarded by cron all day, so it
is the *repository's* copy of the ops entry, not the running one. Merging does not install
anything under `/root/tools/`; `refresh_live.sh` leaves it alone on purpose.

## The ops entry

```
task_queue_ops.py [--json] [--source ui|cli|runner] <action> ...
  version            {"ops_version": <sha256 of the file, 12 hex>, "api": N}
  list               per agent: lock holder, queue in order, quota hint; host file hashes
  head <agent>       the task id that takes <agent>'s lock next ("" when nobody waits)
  cancel <id>        stop a task
```

Exit codes: `0` ok · `2` usage (bad id, bad value) · `3` refused (task ended, action not
allowed for this task) · `4` unknown or pruned task · `5` host failure (systemctl, a write)
· `6` busy (another write to the same task is in flight). With `--json` every action,
failures included, prints one object; failures are `{"ok": false, "code": N, "error": "…"}`.

Every write appends one line to the task's `audit.log`: time, `source=ui|cli`, action,
what changed, and the `ops_version` that did it. Writes to one task are serialised by a
non-blocking lock on `<task>/.ops.lock`; a second write while one is in flight answers `6`.

### cancel

- Only a known task id (`^[a-z0-9][a-z0-9-]*$` with a `meta.env`); anything else is `2`/`4`.
- Unit not active: `ok` if the task already says `cancelled` (idempotent), else `3` with
  its terminal state.
- Unit active: `systemctl stop --no-block`, then up to 4 s for the runner's `on_signal` to
  write its terminal state (`pending: true` if it has not yet). A `cancel-requested`
  marker younger than 30 s makes a repeat a no-op instead of a second stop.
- `was` says what was lost: `queued` (nothing ran — free), `sleeping` (a quota or retry
  wait; the session is kept), `running` (the current step's unsaved progress is lost).
  `session` and `resume` give the command that continues the session.

### Queue order

Each agent has its own lock, so each agent has its own queue; orders never mix across
agents. Among the tasks waiting for one agent's lock:

1. `patrol-*` rounds always go last — their priority is ignored.
2. A manual task that has waited `QUEUE_FAIR_WAIT_SEC` (limits.env, default 14400 s) is
   *protected*: it goes before every unprotected task, and nothing can be placed ahead of
   it any more. A task can only be overtaken during its first hours, so priority cannot
   starve anyone.
3. Protected tasks in `QUEUED_AT` order; the others by `PRIORITY` (higher first), then
   `QUEUED_AT`, then id.

`QUEUED_AT` is when the runner first started waiting (epoch seconds, `result.env`). The
runner registers a waiting task as `.queue/<agent>/<id>` (`PID=`, `QUEUED_AT=`) in its lock
directory and removes the entry when it takes the lock or ends; an entry whose PID is gone
does not count. The lock holder writes `.queue/<agent>.holder` (`ID=`, `PID=`, `SINCE=`).

## Version skew

The chip shows the installed entry's `ops_version` next to the hash of the repository's
copy in the live checkout. If they differ, the entry was merged but not installed (or
edited on the host): run `ops/host/install_task_queue_ops.sh` (it saves the previous copy
and verifies with `cmp`), or `--rollback` to go back. `list` also reports the hashes of
the host-local `run-agent.sh`, `dispatch.sh` and `limits.env`, so a hand edit there is
visible even though those files are not in git.
