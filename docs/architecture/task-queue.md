# Agent-dispatch task queue: who owns what

The dsh sidebar's task chip shows the agent-dispatch queue of this host and lets kcn
steer it. Three parties touch that queue; this page is the contract between them.

| Layer | Where | Owned by | Why there |
|---|---|---|---|
| Plugin source | `examples/dsh/packages/clawock-dsh/src/` | git (this repo) | reviewed code, CI |
| Chat rendering | `examples/dsh/packages/clawock-dsh/src/{desk,panel,text,chat}.ts` | git (this repo) | the same package is an OpenClaw plugin: `/dispatch-list` prints the chip's panel as text, and `/dispatch-stats` prints its frozen task/token totals — the dsh gateway's services (`desk.ts`), the sidebar's view model (`panel.ts`), a text renderer (`text.ts`). OpenClaw loads the installed package through `plugins.load.paths`; read-only |
| Plugin build artifacts | `examples/dsh/packages/clawock-dsh/lib/` | git, regenerated by `npm run build` | dsh loads them without a build step; CI fails on any drift |
| Queue ops entry | `ops/host/task_queue_ops.py` (+ `model_prices.json`) → installed under `/root/tools/agent-dispatch/` | git; installed by `ops/host/install_task_queue_ops.sh` | the only code that writes to a task on behalf of the UI, and the only place the queue order is decided — so it is versioned and tested |
| Installed plugin | `~/.dsh/profiles/<profile>/node_modules/clawock-dsh` | `ops/host/install_dsh_plugin.sh` | generated from a packed tarball; never edited by hand |
| Runner | `ops/host/agent-dispatch/` (`run-agent.sh`, `dispatch.sh`, helpers, `templates/`, its own `tests/`) → installed as `/root/tools/agent-dispatch/`, path for path | git; installed by `ops/host/install_agent_dispatch.sh`, which `refresh_live.sh` runs whenever the installed copy fails its `--check` | tasks execute these files while they are replaced, so every file is installed by rename with a `.before-update` copy; see [The runner](#the-runner) |
| Host policy | `/root/tools/agent-dispatch/limits.env` | host-local, not in git | live admission policy read by the runner, the ops entry and clawock-patrol; see [What stays on the host](#what-stays-on-the-host) |
| Runtime state | `/root/logs/agent-dispatch/<id>/{meta,result,override}.env`, `run.log`, `audit.log`, `.queue/` | the runner and the ops entry | changes every few seconds; never committed |
| Secrets | `/root/tools/agent-dispatch/notify.env` (targets), provider keys | host-local | never in git, reports or memory |

The live checkout (`/root/.openclaw/workspace`) is fast-forwarded by cron all day, so it
is the *repository's* copy of the ops entry and the runner, not the running one. Merging
installs nothing under `/root/tools/`. `refresh_live.sh` (the step that applies a merge to
this host) installs the runner whenever the installed copy differs from the checkout, compared
by content, because cron's pushes fast-forward the checkout too; the ops entry is still
installed by hand, and the chip shows when it lags (see *Version skew*).

## The ops entry

```
task_queue_ops.py [--json] [--source ui|cli|runner] <action> ...
  version            {"ops_version": <sha256 of the file, 12 hex>, "api": N}
  list               per agent: lock holder, queue in order, quota hint, tasks it cannot order
                     (`unqueued`); host file hashes
  head <agent>       the task id that takes <agent>'s lock next ("" when nobody waits)
  cancel <id>        stop a task
  priority <id> <n|top|up|down|reset>
                     reorder a waiting task within its agent's queue
  model <id> <model|keep|default> [<effort|keep|default>]
                     the model/effort of the task's next attempt
  choices <id>       what `model` accepts for this task, and whether it may change now
  retry <id>         continue an ended (failed/cancelled/timed-out) task's session as a new task
  append <id> [--queue] [--text T]
                     add an instruction (stdin) to a live task, same session (dispatch.sh append)
  log <id> [--lines N]   the end of run.log, redacted
  result <id>        the latest final report (read-result.py)
  usage <id>         tokens used and their API-price estimate (text: the result.env lines)
  brief <id>         prompt.md and the appends (inbox/, inbox/delivered/), capped at 64 KB
  summary [--since YYYY-MM-DD] [--agent a,b] [--all]
                     per-agent frozen task/token totals (read-only; see below)
  deadline <id> <+Nh|+Nm|YYYY-MM-DD HH:MM|reset>
  attempts <id> <n|reset>
  resumes <id> <n|reset>
                     the task's deadline / retry budget / quota-resume budget (runner api 3)
```

Exit codes: `0` ok · `2` usage (bad id, bad value) · `3` refused (task ended, action not
allowed for this task) · `4` unknown or pruned task · `5` host failure (systemctl, a write)
· `6` busy (another write to the same task is in flight). With `--json` every action,
failures included, prints one object; failures are `{"ok": false, "code": N, "error": "…"}`.

Every write appends one line to the task's `audit.log`: time, `source=ui|cli`, action,
what changed, and the `ops_version` that did it. Writes to one task are serialised by a
non-blocking lock on `<task>/.ops.lock`; a second write while one is in flight answers `6`.

### cancel

- Only a known task id (`^[a-z0-9][a-z0-9-]*$` with a `meta.env`); anything else is `2`/`4`.
- Unit not active: `ok` if the task already says `cancelled` (idempotent), else `3` with
  its terminal state.
- Unit active: `systemctl stop --no-block`, then up to 4 s for the runner's `on_signal` to
  write its terminal state (`pending: true` if it has not yet). A `cancel-requested`
  marker younger than 30 s makes a repeat a no-op instead of a second stop.
- `was` says what was lost: `queued` (nothing ran — free), `sleeping` (a quota or retry
  wait; the session is kept), `running` (the current step's unsaved progress is lost).
  `session` and `resume` give the command that continues the session.

Cancellation is a durable launch barrier. The CLI and chip use the same audited
cancel operation. `cancel-requested` remains even if stopping the unit fails;
the runner checks it at startup, after quota/retry wakes, and under a per-task
lock before launching an attempt. Old `STATE=cancelled` records also refuse
restart without losing their session or usage. Terminal cancellation clears the
task's wake/slot/queue state. The account-wide quota hint remains an account
availability fact, and cannot schedule or restart the cancelled task. Explicit
`retry` or an append to an ended task creates a new task; it does not remove the
old task's barrier.

### priority

Only a live task of the current runner (`RUNNER_API=2` in its `result.env`) that is
waiting for its agent lock, or asleep on a quota/retry wait (the value then applies when
it re-queues). Refused (`3`): ended tasks, tasks without `RUNNER_API=2` (their runner would
ignore the value), patrol rounds, and a task already running. `top` sets one above every other
reorderable waiter; `up`/`down` swap with the neighbour and renumber the reorderable
waiters so exactly that swap happens (every task whose value changed gets its own
`audit.log` line naming the move); `reset` removes it; an integer sets it (−99..99). A
protected task (below) is not reordered, and nothing can be moved in front of it: that
answers `ok` with `changed: false` and says why. The answer carries the new order.

### model / effort

Written to the task's `override.env` (`MODEL=`, `EFFORT=`) and read by the runner before
**every** attempt, so it applies to the next attempt — the attempt running now keeps its
model. Precedence: an explicit override > the fallback pool > the dispatched default (an
override model becomes the pool's head; failures after it rotate through the rest of the
pool like the ordinary fallback switch). `default` clears a value; `keep` leaves it.
Legal values come from each agent's own source, never a list kept here:

| Agent | Models | Effort flag and values |
|---|---|---|
| claude | the task's own, dispatch.sh's default, those this host has dispatched, the aliases in `claude --help` | `--effort`, the list printed by `claude --help` |
| codex | the task's own, dispatch.sh's default, the visible models in `~/.codex/models_cache.json` | `model_reasoning_effort`, that model's `supported_reasoning_levels` |
| opencode | the task's own, the pool file `opencode-fallback-models` | `--variant`: none (the free pool has no variants) |
| dsh | the task's own, dispatch.sh's default, those this host has dispatched, the two routes DeepSeek's API serves (`DSH_ROUTES`) | `reasoningEffort` in the runner's overlay: `off`, `low`, `high`, `max` |

Changing the model of a session on resume was checked for claude (`--resume` with another
`--model` continues the same conversation, 2026-09-26) and is what opencode's fallback
does every patrol round (`-s` on the next pool model). For dsh the model of every attempt,
a resumed session included, is the overlay the runner writes (checked 2026-10-17 on dsh
0.2.1-rc.2: an overlay naming an unknown model fails a resumed session). It is **not** verified for codex
(its weekly quota was out), so a codex task can change model/effort only before it has a
session.

### retry, append, log, result

`retry` runs `dispatch.sh append <id>` with a fixed "continue from the real state" text on
an ended task that recorded a session and did not finish `ok/DONE`; without a session it
answers `3` (dispatch it again). `append` delivers to a live task only (the chip's
"wrap up" button sends a fixed wrap-up instruction with `--queue`); ended tasks go through
`retry`. The ops append path passes `--require-active`, so a task ending between
its state check and dispatch cannot accidentally start a new task.

Append acceptance and the runner's final inbox check share `inbox.lock`. `inbox-state`
moves from `accepting` to `finishing` to `terminal`. Any other phase refuses append with
exit 3 and writes no instruction; the stderr prefix says how long a retry has to wait:
`task_finishing` (finishing or terminal: usage, notification and wake, usually 1-2 minutes),
`legacy_runner` (a `result.env` but no `inbox-state`: a runner from before this protocol,
which cannot take appends until it ends, possibly hours later; the message names its
`RUNNER_API`), or `task_starting` (neither file yet; seconds). After `task_finishing` or
`legacy_runner` the caller waits for the task to end and appends again, which continues the
session as a new task; nothing is re-queued or started automatically. A successful live append emits
`receipt: {requested_task_id, actual_task_id, message_id, disposition: "accepted"}`;
the ops JSON reply exposes these fields too. Accepted means queued, not completed.
`dispatch.sh inbox <id>` aliases the JSON brief query. A consumed message records its
run number in `inbox/delivered/<message_id>.run`; `disposition=attached_to_run` means it
was put in that run's prompt before CLI launch, not that the model completed it. Runner
api 4 also writes `attempt<N>.env` (`STARTED_EPOCH` once run N launched its CLI past the
cancel barrier; `RC`, `AKIND` ok/quota/error/stalled/stopped and `ENDED_EPOCH` once it
returned), and each brief append carries `run: {started, rc, kind, prompt_kind}` from it
(`null` for older runners). A message taken by a run that never started, on a task that
has ended, is `taken_not_started` with `delivered=false, dropped=true`, and the runner's
final notice counts it among the instructions not delivered. Old consumed files without a
binding say `taken_legacy`; other states are `pending` and `not_delivered`.

`dispatch.sh result <id> [--run N]` includes task/run identity, attempt and quota-wait
budgets, deadline, stop reason (`STOP_REASON`, e.g. `completed` when the model run ended
cleanly with no append waiting, whatever the model's STATUS; `lock_deadline` when the agent
lock is not won before the deadline, also after a quota wait), notification result and any
recorded wake states. The
runner atomically saves its own terminal explanation in `runner-summary.txt`, so a
zero-attempt session-lock refusal is queryable without a model report. An incomplete
latest run never falls back to an earlier successful report. `--run N` selects a
historical model report, with a warning that the envelope describes the latest task
state. A terminal append still creates a separate task and now stores `PARENT_TASK_ID`;
its output ends with `receipt: {requested_task_id, actual_task_id: <the new task>,
message_id: null, disposition: "continued_as_new_task"}`. `dispatch.sh status <id>` prints
`parent:` and `children:` (tasks whose `PARENT_TASK_ID` is this id) and one `run N:` line per
`attempt<N>.env` (prompt kind, started yes/no, rc, result).
`dispatch.sh log <id>` aliases ops log. `status --all` lists all retained tasks including
patrol rounds; the default list stays at ten and includes notification/stop fields.

### usage — tokens and an estimate, not a bill

`usage` reads the agent's own session record and never guesses:

| Agent | Record | What is counted |
|---|---|---|
| claude | `~/.claude/projects/*/<session>.jsonl`, each assistant line's `message.usage` | deduplicated by message id (claude repeats one API message's usage on every content-block line); cache writes split into 5-minute / 1-hour by `usage.cache_creation` |
| codex | `$CODEX_HOME/sessions/**/rollout-*-<session>.jsonl`, `token_count` events | `total_token_usage` is cumulative per process: repeats add nothing, a resumed process restarts from zero; `cached_input_tokens` is part of `input_tokens` |
| opencode | `~/.local/share/opencode/opencode.db`, table `message` | `tokens.input/output/reasoning/cache.read/cache.write` and opencode's own `cost` |
| dsh | the task's own `attempt<N>.jsonl` (`dsh --json`), each `step_end` event's `usage`; the model is that attempt's overlay `attempt<N>.yml` | `inputTokens` (excludes cache reads), `outputTokens`, `cacheReadTokens`, `cacheWriteTokens`; the files are the task's own, so no time window is needed |

The session is `SESSION` in `result.env` (older tasks: `session_id` in `attempt*.json`). New paid tasks use `USAGE_START_EPOCH` (first run, after queueing) through
`FINISHED_EPOCH` (before notification/lock release). Missing-timestamp records are
excluded. A finished legacy paid task without an end boundary returns its frozen
`TOKENS_*`/`COST_USD` values with `models: [MODEL_USED]` (the model it last ran; the frozen
totals have no per-model split), or unknown when absent; it never rereads the later shared
session. Zero-attempt tasks do not claim another writer's session usage. Live legacy
tasks and OpenCode retain the dispatch-time lower bound (`meta.env CREATED`). The price per model is `ops/host/model_prices.json` (source and date in
the file, installed next to the entry): the amount is **what the tokens would cost at API list
prices**, an estimate — claude and codex run on subscriptions here, and no subscription price is
in the table. claude rows come from Anthropic's API price table; codex's `gpt-*` rows (2026-09-28)
from OpenAI's API pricing page (`sources.openai` in the file: URL, date, standard short-context
tier; its cached-input rate is `cache_read`). DeepSeek's rows (`sources.deepseek`, 2026-10-17) are
its peak rates; dsh tasks are the only ones billed per token here, from the DeepSeek balance, and
off-peak hours cost half, so their estimate can read high. A model without a row keeps its tokens and has no
amount (`—` on the chip), never a guessed one; an
opencode task is `free` when opencode reports cost 0 and every model is in the free pool file or
ends in `-free`. Checked on a real task: the estimate for `add-side-aggression-20260926-151620`
($14.02) equals the `total_cost_usd` claude itself reported for that session.

The runner (api 3) runs `usage` after every attempt and at the end, and keeps the answer in
`result.env` (`TOKENS_IN`, `TOKENS_CACHE_W`, `TOKENS_CACHE_R`, `TOKENS_OUT`, `TOKENS_TOTAL`,
`COST_USD`; empty when nothing was found). A live task's figures are therefore as of its last
finished attempt.

### summary — totals over the frozen results

`summary [--since YYYY-MM-DD] [--agent claude,codex,opencode,dsh] [--all]` (`dispatch.sh summary`)
counts, per agent, tasks by runner `STATE` and by model `OUTCOME`, and adds up the
`TOKENS_TOTAL` / `COST_USD` each terminal task froze into `result.env`. It never rereads a
session (a later task continuing the same session would be counted twice). An empty value is
`tokens_unknown` / `cost_unpriced`, never 0; `free` is counted apart; live tasks are counted as
tasks but stay out of the totals. Patrol rounds are left out unless `--all`. The amount is the
same API list-price estimate as `usage` (`cost_kind: estimate`): there is no per-task
attribution of subscription quota (the 5h/weekly windows are account-wide and shared with
interactive use), so the summary does not offer one.

Two read-only surfaces consume exactly this answer, never a second count of their own: the
task chip's **stats tile** and OpenClaw's **`/dispatch-stats`** command. Both default to the
last seven local calendar days with patrol rounds excluded; the command accepts `7d`/`30d`,
`all`, `YYYY-MM-DD`, `patrol` and `plain` (e.g. `/dispatch-stats 30d patrol`), while the chip
keeps its seven-day window. The tile carries the task count, `token` total, `API estimate`
and a completion bar; it opens a chart layer (token bars and per-agent completion bars) and
is read lazily through the `taskStats` Remote method when the panel opens, not on the queue's
poll. The command prints a five-column table (Agent / done-ended / partial / unfinished /
token · API 估价), with `plain` as the bar fallback. Its title carries the total and live
count; there is no trailing description. An unpriced cell reads `—`, the header says
`API 估价`, and the chip's chart layer keeps one short `API 估价非订阅额度` line; the CLI
`summary` still reports `tokens_unknown` and `cost_unpriced` for a caller that needs the
counts. A failed read is said as a failure, not drawn as zeroes.

### brief — the task's instructions, read-only

`brief` answers `prompt.md` (the brief as dispatched, with its dispatch contract) and every append:
`inbox/*.md` not delivered yet, `inbox/delivered/*.md` delivered, in file-name (time) order. The
answer is capped — the brief at 48 KB, the appends at 16 KB together — and says so, with each
file's path so a reader can open the whole file. In JSON: `truncated` (prompt.md was cut; its real
size is `brief_bytes`), each append's own `truncated` and `bytes`, and `appends_truncated` /
`dropped_bytes` for the whole answer. In the default text answer, each cut file's header carries
`[truncated: <real> -> <shown> bytes; full text: <path>]`, and a last line gives the bytes not
shown. Before #1988 the text answer dropped them without a word, exit 0. Nothing edits a brief: change a queued task's `prompt.md` before it starts, or
`dispatch.sh append` (`--queue` while it runs).

### deadline, attempts, resumes — the task's budgets

| Budget | Owner of the dispatched value | Changed by | Bounds |
|---|---|---|---|
| deadline (`DEADLINE_EPOCH`) | `meta.env` (dispatch.sh, at most 72 h after dispatch) | `deadline <id> …` | ≥ now + `MIN_RUN_SEC` + `KILL_MARGIN` (600 + 70 s); ≤ dispatch + 72 h (the dispatch ceiling kept); an expired deadline is never moved earlier |
| retries (`MAX_ATTEMPTS`) — failed or stalled attempts | runner default 3 (`meta.env` may carry one) | `attempts <id> n` | 1..10, not below the attempts already made |
| quota resumes (`QUOTA_RESUMES`) — each one replays the session's context | `meta.env` | `resumes <id> n` | 0..6, not below the resumes already used |

The two retry budgets are different money: a retry re-runs a failed attempt; a quota resume
continues the session after a quota wait and pays to replay its context (cache reads).

The entry writes the new value to `override.env` (`reset` removes it; a value equal to the dispatch
record is not stored) and audits it. A runner of **api 3** rereads these keys at every poll of its
lock wait and before every attempt, and publishes what it uses in `result.env`
(`DEADLINE_EPOCH`, `MAX_ATTEMPTS`, `QUOTA_RESUMES`) — the chip shows those, not the dispatch record.
When it applies:

- **waiting** (queued for the lock, asleep on quota/retry): at the next poll, seconds;
- **running**: the attempt in flight keeps the time cap it started with; the change applies to
  the next attempt and to every wait after it;
- **runner api 2** (started before api 3 was installed): refused (`3`). It read `meta.env` once at
  start and armed its outer `timeout` from the deadline, so the change could not apply.

A write to an ended task is `3`; a value out of bounds is `2`. Nothing restarts the task's unit.

What made this necessary (a real attempt, 2026-09-27, to carry three queued tasks past a weekly
quota reset):

- `meta.env` is sourced **once**, when the runner starts; editing it changes nothing for a live
  task. `prompt.md` is read at the start of **every attempt**; do not confuse the two.
- The unit is a transient `systemd-run` unit: `systemctl restart` answers `Unit … not found`. It
  can only be recreated as dispatch.sh does (`systemd-run --unit agent-dispatch-<id> --collect
  --quiet --description "agent-dispatch <agent>: <name>" -p TimeoutStartSec=infinity
  -p TimeoutStopSec=90s -p KillMode=control-group /root/tools/agent-dispatch/run-agent.sh <dir>`).
- A restart loses `QUEUED_AT` (kept in memory and `result.env`; a new runner does not read it
  back), so the task loses its place in the queue.
- A runner before api 3 wraps itself in `timeout -k 80 $((deadline - now - 10))` at start: a
  later deadline in any file does not stop that timer. Api 3 arms the outer timer at the
  dispatch + 72 h ceiling instead and enforces the deadline itself (attempt caps, lock and slot
  budgets, quota and retry sleeps all read the current value).
- Stopping a runner with TERM runs `on_signal` → `finish()`, which sends a "cancelled"
  notification that is not true for a restart; SIGKILL sends none but writes no terminal state
  either. Neither is a way to change a budget — that is why the change goes through
  `override.env` and never through a restart.

### Queue order

Each agent has its own lock, so each agent has its own queue; orders never mix across
agents. Among the tasks waiting for one agent's lock:

1. `patrol-*` rounds always go last — their priority is ignored.
2. A manual task that has waited `QUEUE_FAIR_WAIT_SEC` (limits.env, default 14400 s) is
   *protected*: it goes before every unprotected task, and nothing can be placed ahead of
   it any more. A task can only be overtaken during its first hours, so priority cannot
   starve anyone.
3. Protected tasks in `QUEUED_AT` order; the others by `PRIORITY` (higher first), then
   `QUEUED_AT`, then id.

`QUEUED_AT` is when the runner first started waiting (epoch seconds, `result.env`). The
runner registers a waiting task as `.queue/<agent>/<id>` (`PID=`, `QUEUED_AT=`) in its lock
directory and removes the entry when it takes the lock or ends; an entry whose PID is gone
does not count. The lock holder writes `.queue/<agent>.holder` (`ID=`, `PID=`, `SINCE=`).
The runner looks one poll after it (re-)enters the queue, so tasks that enter together
(at a quota reset) are all registered before one is picked; if the entry is missing or
fails, a manual task takes the lock when it is free (the old behaviour) and a patrol round
still never takes it while a manual task of its agent is registered.

### Tasks without RUNNER_API 2

Only a task whose `result.env` says `RUNNER_API=2` registers in `.queue/`, writes
`QUEUED_AT` and honours `override.env`. A live task without it (a runner from before
2026-09-26, or one started by hand) is never shown as an empty queue (kcn 2026-09-26):
`list` names it under its agent's `unqueued` with the reason, `head --json` adds it to its
`note` (the bare-id text answer the runner reads is unchanged), and `priority`/`model`
refuse it (`3`). A held lock without a live holder file is reported as
`held: true, id: null` with a note, never as free.

Until 2026-09-27 the entry also parsed such tasks' `run.log` (`waiting for <agent> lock`,
`lock held`) to place them first in their queue, flagged `legacy`. That branch was removed
once no older runner was left (`list` showed no legacy row and every live `result.env`
had `QUEUED_AT` and `RUNNER_API`); the `legacy`/`holderLegacy` fields are gone from the
chip's wire too.

### Quota waits release the lock

A task that hits a quota limit sleeps until the reset **without** its agent lock (before
2026-09-26 it kept it: a claude task asleep on its 5-hour reset held `claude.lock` for four
hours while three tasks queued). It keeps its session lock (`session-<id>.lock`, taken as
soon as the session is known), so no second task can resume the same session meanwhile,
and it writes `.queue/<agent>.quota` (`UNTIL=`, `BY=`). A task that takes the lock while
that hint is in the future releases it again and waits for the same reset (plus two polls)
without spending an attempt, a quota resume or a notification — the limits are per
account. At the reset the sleeper re-queues with its original `QUEUED_AT`; the first
attempt that gets through deletes the hint.

A task that ends on quota (`reset_after_deadline`, `no_session`, `quota_resume_budget`)
deliberately writes no hint: nobody would be left to clear it, so one misread reset (a weekly
one is days away) would hold every later task of the agent without a single attempt, while the
attempt a hint saves fails fast on an exhausted account. Admission is a prompt only: a new
claude/codex task prints the account's quota line (`quota.mjs`, 90 s cache, 8 s bound) and
starts anyway. The runner never refuses on a low balance, never changes the model or effort it
was given, never moves a task to another agent, and does not raise the resume budgets
(`QUOTA_RESUMES` stays inside `MAX_ATTEMPTS` and the deadline; the quota stops seen so far were
resets past the deadline, which more resumes would not reach; a longer `--deadline` does).

Nothing is replayed automatically (2026-10-16): not an append refused while a task finishes
(the refusal queued nothing and says when to retry; continuing would be one more paid run nobody
asked for, and the race hit 1 of 360 tasks before the handshake), not an append whose run
failed (in the 8 tasks where a run carrying appends ended in quota or an error, all 18 of their
delivered appends were in the session record, so a resend would run them twice), not one taken by a run that never started (that happens only
when a cancel or the deadline stops the task, where re-sending contradicts the stop), and not a
failed notification or wake turn (the 10 tasks whose legs both failed include three within four
seconds of each other, a shared cause a retry would hit again; a wake turn may have acted).

### Native background sessions (`claude --bg`)

Claude Code 2.1.303 can run a session in the background (`claude --bg`, then `claude agents`,
`attach`, `logs`, `stop`). kcn asked (2026-10-20) whether the runner's quota resume should move
onto it. It does not, for four reasons measured on this host that day:

- **It does not wait out a usage limit.** The CLI's "continuing automatically at <reset>" is
  armed only when `isInteractive && !bgSession && !remote` (the bg check reads
  `CLAUDE_CODE_SESSION_KIND=bg`, which every background worker carries), and handing a session
  to the background cancels a pending one ("this session moved to the background, so the task
  will not resume on its own when the usage limit resets"). A background session refused by its
  limit sits `blocked` in `jobs/<id>/state.json` until somebody acts.
- **The daemon is not a service.** `claude daemon` says "Service install is disabled in this
  version — the daemon runs on demand and exits when the last client disconnects". The first
  `--bg` client starts it in its own cgroup, and every worker is its child: a session started
  from another cgroup while it lived landed in the daemon's. Started inside an
  `agent-dispatch-<id>` unit, it and every background session of the host would be killed when
  that task ends (`KillMode=control-group`).
- **It retires settled sessions under memory pressure.** `daemon.log`: "low memory (572MB free)
  — retiring settled workers before spawning …", "bg settled 041ab07a (killed)" — that session
  was the one `blocked` on its limit.
- **No result contract.** There is no `--output-format json`; the end state is
  `state.json` (`done`, an `output.result` that dropped the reply's `STATUS:` line) plus a
  fullscreen terminal log, and an untrusted directory refuses to start (`Workspace not trusted`).

`claude -p` already outlives SSH (the unit is not attached to a terminal), and the runner's own
sleep-then-`--resume` is the only thing on this host that resumes a session at its reset. So
the integration goes the other way:

- **`dispatch.sh adopt <bg-id|session-id> [--dry-run] [options] [< instructions]`** turns a claude
  session dispatch did not start into a task that resumes it: a background session, or a
  terminal session whose CLI died while it waited for the reset (2026-10-20 00:04, SSH dropped
  and took `765798b5` with it; nothing ran at 02:10). `claude-session.py resolve` finds the
  session id, the directory it was started in (the transcript's project, not its last `cd`:
  `765798b5` had moved to `/root/wt-card`, but resumes from `/root`) and the limit it stopped on,
  and asks `claude agents --json` whether anything has it open. A working background session,
  any live interactive or headless process (a terminal, a dispatched task's `claude -p`), or no
  answer at all is refused. Otherwise the task is dispatched as `claude --resume <id> --cwd <dir>`
  with the instructions on stdin (or a plain continue), and a background copy still open in the
  daemon is stopped with `claude stop` last, after every dispatch check passed and before the
  unit starts, so one process writes the transcript. If the limit has not reset yet, the first
  attempt meets it and the ordinary quota wait above takes over. It is an explicit command: no
  session is adopted, stopped or resumed on its own.
- **The runner exports `CLAUDE_CODE_DISABLE_AGENT_VIEW=1`** for every agent, so no task starts
  the shared daemon inside its unit (`'--bg' is disabled by CLAUDE_CODE_DISABLE_AGENT_VIEW`;
  `claude -p` is unaffected).

Unverified: whether a background session survives an actual SSH disconnect (it has no
controlling terminal, so it should), and how the daemon behaves once a later version installs it
as a service; re-read this section after a Claude Code upgrade that changes `claude daemon`.

`audit.log` one line per write.

## Mandate

Every task `dispatch.sh` creates gets `<task dir>/mandate.json` before its unit starts. It is
the machine-readable version of what the brief used to imply: the policy version (a hash of
`dispatch.sh` and `run-agent.sh`), the source that accepted the task, its strength, its
working root, the allowed host actions, and the notification rule. It is written once, mode
`0444`, and never rewritten; a wider request needs a new task.

| Action | Default | `--no-restart` |
|---|---|---|
| `gateway.restart` | `allow` | `deny` |
| `live.refresh` | `allow` | `allow` |

The default is kcn's 2026-11-01 rule: making a task's change effective may restart the
serving process without asking. `--no-restart` denies it, and `ops/host/refresh_live.sh` checks
*both* actions before it writes, so a denied task cannot half-apply a merge. `ops/host/restart_gateway.sh`
checks `gateway.restart` before `openclaw gateway restart`; use that wrapper rather than the
bare command, and write a `RESTART:` line in the report.

A denial is appended to `<task dir>/mandate-violations.jsonl` (time, task, policy version,
action, source, pid) and the caller exits `3`. A task from before mandates, or an interactive
shell, has no `mandate.json`: the guards report the missing file and proceed. This is an
audit record and a guard for the host scripts we own, not a sandbox — a task that executes a
program by absolute path is outside it, matching the external prototype's own statement about
its wrappers. `dispatch.sh mandate <id> [check <action>]` reads or checks one.

## The runner

`run-agent.sh` runs one task inside a transient systemd unit that `dispatch.sh` starts
(`systemd-run --unit agent-dispatch-<id> … run-agent.sh <task dir>`): it waits for its agent's
lock in queue order, takes a run slot, runs the CLI attempt by attempt, handles quota waits,
retries, stalls and appends, writes `result.env`, and sends the notification. Its source is
`ops/host/agent-dispatch/`, laid out exactly like the installed directory:

```
ops/host/agent-dispatch/
  run-agent.sh  dispatch.sh            the runner and the host CLI (RUNNER_API=5)
  read-result.py quota.mjs             `dispatch.sh result`, the quota / dsh balance line in notices
  resource-pressure.sh                 memory-pressure reading shared with clawock-patrol
  probe-free-models.sh                 finds dead models in the opencode free pool
  opencode-fallback-models             that pool, in order (read at dispatch time)
  claude-session.py                    `dispatch.sh adopt`: finds a claude session dispatch did not start
  mandate.py                           create/check the task mandate, record a denial
  templates/review.md                  `dispatch.sh --template review`
  tests/run-tests.sh tests/bin/        fault-injection suite with fake claude/codex/opencode/dsh/openclaw
  tests/test_limits.py tests/test_read_result.py tests/test_claude_session.py tests/test_mandate.py
```

It sits next to `task_queue_ops.py` but is a different install target: the ops entry keeps its
own installer and its own place in `ops/host/`.

### dsh as an agent

`dispatch.sh dsh` (2026-10-17) runs DeepSeek Harness's one-shot headless profile, not the
web UI: `dsh --profile headless --patch attempt<N>.yml --json [--session-id <id>] -` in the
task's cwd, the prompt on stdin. It needs dsh 0.2.1 or later on the runner's PATH. The
headless profile answers one task and exits: 0 only when the turn completed; a failed turn
names its error code in the `turn_end` event and on stderr, and `QUOTA` (DeepSeek's
insufficient balance) is a quota stop with no reset time. Three things differ from the
other CLIs:

- The model and effort are a patch overlay the runner writes per attempt (`agent-default-model`:
  `provider`/`model` from `MODEL=<provider>/<model>`, `reasoningEffort` from `EFFORT`). The
  default is `deepseek-official/deepseek-flash` (DeepSeek-V4.1-Flash-1017) at `max`, the
  headless profile's own default.
- The headless profile does not read dsh's credential store; the attempt's subshell exports
  the keys stored under `refs:` in `~/.dsh/.credentials.yaml` (only those not already set).
- It is paid per token from the DeepSeek balance. There is no subscription window and no
  percentage to quote, so the finish notice appends the account's **money** balance from the
  same `refs:` seam (`quota.mjs`, same 90 s cache and last-good fallback: `余额 ¥… · 赠金 ¥… ·
  充值 ¥…`) instead of the claude/codex window line; the dispatch output keeps no quota line.
  `usage` prices the run at list rates.

```bash
ops/host/install_agent_dispatch.sh            # parse-check, then per file: .before-update, install by rename, cmp
ops/host/install_agent_dispatch.sh --check    # exit 1 when an installed file differs, or limits.env lacks a key
ops/host/install_agent_dispatch.sh --rollback # undo the last install that changed something (and only that)
```

The installer refuses to run when the host's `limits.env` is missing or lacks a key the runner
needs. It records what it replaced in `.install-agent-dispatch.last`, so a rollback does not
restore an older `.before-update` left by a hand edit. A running task keeps executing the
file it opened (a rename leaves that inode alone; an in-place copy would corrupt a bash script
mid-read); the next task starts on the new one.

Tests. `.github/workflows/dispatch-runner.yml` runs the suite on every PR that touches the
runner, the ops entry, either installer or `patrol.sh`. It stages the files at their host path
through the two installers and runs them as root, as on the host, one matrix leg per group.
It is not a required check, and its trigger is path-filtered so other PRs start nothing. By
default it runs the non-slow matrix in `.github/workflows/dispatch-runner.yml` (every group
except the two below): the longest, `budget`, took 158 s on the first run, less than `validate`. `stall` (198 s) and `quota` (256 s)
are almost entirely real waiting: stall timers running out, a quota reset minutes away. They
run on demand (`workflow_dispatch` with `slow`), or on the host:

```bash
AGENT_DISPATCH_RUNNER=<staged run-agent.sh> DISPATCH_TEST_CASES=stall,quota \
  bash <staged>/tests/run-tests.sh
```

`tests/test_install_agent_dispatch.py` (in `validate`) holds the installer's file list equal to
the tracked files and checks install, `--check` and `--rollback` in a temp directory.

### Notifications

At the end of a task, and when it starts a quota wait, the runner sends one message per leg of
the task's `NOTIFY` list (`weixin`, `telegram`, both by default, `none` for patrol rounds).
Each leg is `openclaw message send --channel … --target …` with the targets from `notify.env`.
The legs run in parallel, each once, with a time limit: 60 s for the end-of-task and the
quota-wait notice, 30 s on the cancel path (bounded by the unit's stop budget).

**When the end notice is sent.** The agent's last `NEEDS:` line is a structured fact, not
prose to guess from. `ATTENTION=person` (a blocked/failed/timeout/quota end, `PARTIAL`, or a
`DONE` whose `NEEDS` names an action) sends the notice and wakes the dispatching session. A
clean `DONE` with `NEEDS: none` records `NOTICE=suppressed` and sends nothing: `result.env`
and the chip still show the outcome, and `/dispatch-list` remains the place to look. A missing
`NEEDS` line is `unknown` and keeps the old notice — silence must be reported, not inferred.
A `cancelled` task also keeps its notice. The same gate decides the wake turn below.

The end-of-task notice ends with two separate optional lines, never one combined amount:
`额度：…` is what the agent's account has left (claude/codex's quota window, or dsh's
DeepSeek money balance) while `花费：…` is what this run used at API list prices
(`花费：$0.26（按 API 价估算）`, or `花费：免费（opencode 免费池）`). They point in
opposite directions and use different currencies, so each keeps its own label and line.
`update_usage` fills `COST_USD` after every attempt and again before the notice, bounded by
`FINISH_USAGE_TIMEOUT` (20 s normally, 8 s on the cancel path). An empty `COST_USD` omits
the cost line rather than printing `$0`: an unknown amount is not a free run. A value left
from an earlier read is marked `截至上一次读数`, and a priced `$0.00` still prints (the
estimate did see priced tokens).

Delivery is **best-effort**. A failed leg never changes the task's state, is not retried,
and raises no alarm. It is one `notify: send failed (<leg>): rc=<n> <reason>` line in `run.log`
(the reason is the last stderr line of the send, redacted and cut to 200 characters, or
`timed out after <n>s` for rc 124), and
`NOTIFIED` / `NOTIFY_FAILED` / `NOTIFY_AT` in `result.env`, which the chip shows as the
receipt icons. A successful command does not establish receipt or reading on a
phone; a failed command does not establish that the other leg failed. The CLI result
labels disabled, unknown, send succeeded, partial failure and failure separately.
Wake events snapshot these actual fields, and never claim that kcn has already read
the notice. No automatic notification resend is added.

What the legs did from 2026-09-26 to 2026-09-28 (every `notify:` line in `run.log`):

- **WeChat** failed on every send from at least 09-26 03:25 to 09-27 20:52, and has
  delivered every send since 09-27 22:23. This is the known WeChat token problem: the
  per-conversation token behind the `openclaw-weixin` channel lapses, and every send fails
  until it is renewed. It is not fixed here and can come back.
- **Telegram** delivered every end-of-task notice. It failed four times, all on 30-second
  notices (three quota-wait notices, one cancel), each after exactly the 30 s limit. The CLI
  is slow to start on this host: a `--dry-run` of the same command, which sends nothing, took
  13 s alone and 25 s with both legs starting together. So a real send can take longer than
  30 s. Neither the configuration nor the network was the cause. The quota-wait notice has
  had 60 s since #2057; a cancel notice keeps 30 s, the most the unit's stop budget
  (`on_signal`) leaves, so on a busy host a cancel can still go unannounced on Telegram.

### A turn in the session that dispatched

The legs tell kcn. OpenClaw mirrors the WeChat send into this chat's transcript; Telegram
goes to its own target and does not enter this session. Neither send starts a turn: without
wake, the assistant learns that its task ended only when
kcn next writes. So a task also reports to the OpenClaw session it was dispatched from, as one
turn in that session (kcn 2026-10-12: notify where the task was dispatched, in the same
session). `wake-session.py` owns all of it; the runner calls it once next to `notify()`.

| Question | Rule |
|---|---|
| Which session | `ORIGIN_SESSION` in `meta.env`, recorded by `dispatch.sh`: `--origin-session <key>`; else `OPENCLAW_MCP_SESSION_KEY` (a CLI-backend turn has it); else, when `dispatch.sh` is a descendant of the gateway process, the one chat whose `sessions.json` row says `running`. Two chats mid-turn is ambiguous and records nothing. A task continued with `append` reports to whoever continued it, else to its first origin |
| No session | dsh, a terminal, cron, patrol: the task sends its messages and starts no turn. There is no conversation to continue, and a turn in the main session would arrive without context |
| Which sessions can be woken | `agent:<id>:main` and `agent:<id>:<channel>:direct:<peer>`. Cron, dreaming and other isolated sessions have no reader |
| Which events | the end of a task whose end notice was sent (`ATTENTION=person` or `unknown`) and its first quota wait. A suppressed `DONE` + `NEEDS: none` and a `cancelled` task start no turn. `--notify none` tasks (patrol rounds) never wake |
| How | `openclaw agent --session-key <origin> --message-file …`, in a transient unit `agent-dispatch-wake-<hash>-…`, because the turn outlives the runner. The reply is not delivered to the chat: the legs are the one message kcn gets about an event, and a delivered reply was a second message about the same task in the same WeChat chat. When the assistant carried on with work kcn had asked for, it says so with its own message tool |
| What the turn is told | a pointer: the notice's first line (task, agent, state, the model's own status), the task id and `dispatch.sh result <id>`. Not the notice: the legs carried that, and the WeChat leg lands in the same chat, so a copy in the turn showed kcn the same text twice. The legs never depend on the turn: `wake.off`, the hourly cap and the chain depth only decide whether a turn starts |
| Once per event | the call sits beside `notify()`, not in its per-leg loop: two legs, one turn. Pending copies coalesce. Only a successful turn (`rc=0`, `status=ok`) writes the marker per (session, task, event) under `/root/logs/agent-dispatch/.wake/<hash>/seen/` and removes its spool files. Acknowledged `end` and `quota` events do not wake again, across unit restarts |
| Bursts | events that arrive while a turn runs are spooled; the next turn takes all of them. At most `WAKE_MAX_PER_HOUR` (6) attempts per session in a rolling hour, including failures and explicit retries; the rest stay pending with a `wake: skipped` line, without scheduling another attempt |
| Chains | a task dispatched while a wake turn runs in its session gets `WAKE_DEPTH` + 1, and a task at `WAKE_MAX_DEPTH` (2) does not wake. So kcn's instruction can be followed by two automatic hops, not by a loop |
| Failure | never the task's problem: `wake: turn FAILED …` in `run.log`, followed by the retry command. Its batch stays in `spool/`; repeat `wake-session.py enqueue <task-dir> <event> <text-file>` or explicitly run `wake-session.py drain <hash>` to retry under the same guards. No automatic retry: a failed turn may already have acted, so replay can repeat work |
| Turn budget | `WAKE_TURN_TIMEOUT_SEC` defaults to 600. The pointer tells the assistant its budget and to finish currently available follow-up work without sleeping or polling for other tasks, cooldowns or CI |
| Off | `touch /root/tools/agent-dispatch/wake.off`; `rm` it to turn it back on. Read at every event, so it also stops tasks already running. The three numbers can be set in `limits.env` (`WAKE_MAX_PER_HOUR`, `WAKE_MAX_DEPTH`, `WAKE_TURN_TIMEOUT_SEC`) |

The gateway's HTTP hooks (`/hooks/wake`, `/hooks/agent`) are not used. `/hooks/wake` only
reaches the fixed main session. `/hooks/agent` needs `hooks.allowRequestSessionKey`, and this
gateway is published through Tailscale Funnel, so that endpoint would be on the internet with
one bearer token between a caller and a turn in kcn's chat. The CLI uses the gateway's existing
authenticated RPC: no configuration change, no restart.

`wake.off` is the host owner's switch. The hourly attempt cap prevents repeated failures
or retries from causing unlimited turns; the successful-event marker prevents duplicate
wakes; the depth cap prevents recursive wake chains. A switch or hourly-cap skip during
drain preserves queued events for explicit retry. Existing empty `seen/` markers retain
their legacy deduplication behavior on upgrade; installation does not reconstruct or replay
events already lost by older versions.

Scheduled jobs do not wake a session. Each already is an agent turn that delivers its own
report, and that report is mirrored into the chat transcript like any message, so the chat
knows what was sent. A second turn after it would produce a second message about the first.
A job that fails is the watchdogs' and cron-health's business.

`run.log` lines, in order: `wake: queued (end) for agent:main:<channel>:direct:…`, then
`wake: turn ok in … (rc=0 status=ok run=<id> 41s, 1 event(s) in this turn)`.

## Reading a task's history

The existing `log <id> --json` answer includes a `timeline` next to `lines`; its text answer
remains the log tail. The dsh detail's **Progress timeline** button uses that same read-only
RPC, so the new client can read the updated installed ops entry without a host restart.
It reads stamped supervisor events, append submission filenames, audit writes and the latest
notification receipt, sorted by the recorded local timestamp. Append submission and delivery
are distinct events. A `result.env` UPDATED write is not a completion event.

This is a view of existing evidence, not a new runner state machine. Old logs can have gaps;
missing logs are labelled. A large run log is bounded to a 2 MiB head and 2 MiB tail, the audit
read to 256 KiB, and the displayed event list to its first/last 100 events. Omitted bytes/events
and audit truncation are explicit. Full log preview remains available. Reads do not append an
audit record, consume attempts or change task state.

The brief's append files remain the durable instruction records. An append left in the
inbox of a terminal task is `dropped`, not pending. Unstamped runner drop records are
shown at their following task-end boundary, explicitly labelled with that timestamp basis. The client displays their
chronological sequence number, timestamp, delivered/pending status and first-line excerpt;
opening a row previews its source file. The filename is its identity, and these numbers are
not immutable snapshots of the entire brief/plan. PRs and commits remain the code diff history.

Recent completions read every non-active, non-patrol result's terminal state and UPDATED before
capping the list. File mtime does not select candidates; missing UPDATED sorts last. Detailed
logs are read only for the chosen rows. This reader change requires the dsh host and gateway
to reload their modules; a no-restart client install alone does not change that in-memory code.

Deliberately out of scope, each for a recorded reason:

- **Parent/child tasks, a dependency graph, fan-out/join.** Nothing here depends on it, and
  one slot per agent on a two-core host is the real limit. Relations go in the brief or the PR.
- **A phase board with drag-to-change-state.** There is no plan-approval or diff-acceptance
  lifecycle to project; provider → queue → detail fits a narrow sidebar. A failure is an end
  result and a quota wait is automatic, so neither is "waiting on a person".
- **A native `events.jsonl` written by the runner.** It would be an unambiguous source, but it
  needs atomic runner writes, a failure policy and compatibility with old tasks. Until that is
  a runner change with fault injection behind it, the timeline stays a reading of existing logs.
- **Per-model cost charts and live token counters.** Nothing collects continuously, and a
  subscription window is not an API bill.

### Find earlier work without loading whole conversations

This applies the lightweight-identifier / just-in-time retrieval pattern described in
[Anthropic's context engineering article](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
(published 2025-09-29, consulted 2026-11-01): find a relevant record before loading its body.
The existing task records are the source of truth; retrieval adds no new memory or authority.

`dispatch.sh history [--json] [query]` searches task **metadata** (id, name, runner state,
model outcome), newest creation first. Query words are case-insensitive AND substrings,
including Chinese. Use `--agent codex`, `--state ok`, `--since 2026-11-01`, and `--limit 10`
(1–50). Patrol rounds are excluded unless `--all` is supplied. This includes live and legacy
tasks; an absent result is `pending`, absent attention is explicitly `unknown`.

```bash
/root/tools/agent-dispatch/dispatch.sh history --json 'brief' --agent codex --limit 5
/root/tools/agent-dispatch/dispatch.sh history 'brief' --agent codex --limit 5 --before TASK_ID
/root/tools/agent-dispatch/dispatch.sh inbox TASK_ID
/root/tools/agent-dispatch/dispatch.sh log TASK_ID
/root/tools/agent-dispatch/dispatch.sh result TASK_ID
```

Keep the same filters on the next call and use `next_before` as `--before`. The exclusive
cursor is the task's `(CREATED, id)` pair, so newly created tasks do not shift subsequent pages.
The cursor task must still exist. Creation times use the host's recorded local time; records
without a timestamp sort last and are excluded by `--since`. Each displayed field is redacted,
whitespace-normalized and capped at 240 characters. `has_more` reports another page, not a
frozen snapshot: concurrent completions can change state/outcome matches.

The owner is `task_queue_ops.py history`; it reads only `meta.env` and `result.env`, does not
scan prompts, reports or sessions, does not call systemd, and writes no index. It scans local
metadata per request, separate from active queue polling. The output deliberately omits
origin/session ids and brief contents. Retrieve `inbox`, `log` (including its existing JSON

Wake observations are separate from task outcomes: `wake-quota.json` and `wake-end.json`
record `pending`, `inflight`, `failed` or `acknowledged`, event ID, attempt count,
`last_error` (return code/status only) and acknowledgment time. `status <id>` and
`result <id>` show them. A missing observation on an older event remains unknown.
Acknowledgment still requires both rc=0 and status=ok; a failed turn keeps the spool
for the existing later drain path. These observations do not add retries or replay.
